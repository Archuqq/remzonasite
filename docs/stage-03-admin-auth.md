# Этап 3 — Авторизация админ-панели

## 1. Что сделано

- Закрыты `/admin/**` и `/api/admin/**` подписанной HS256 JWT-сессией; страница входа и публичные страницы отделены route groups.
- Добавлены login/logout и смена пароля с bcrypt cost 12, одинаковым ответом на неизвестный логин/неверный пароль и ограничением перебора.
- Для изменяющих запросов проверяются `Origin`, `Host`/`X-Forwarded-Host` и `Sec-Fetch-Site`; cookie имеет `httpOnly`, `sameSite=lax` и `secure` в production.
- Добавлена защита на уровне Next.js 16 `proxy.ts` и повторный `requireAdmin()` в защищённых API handlers и панели.
- Реализованы адаптивные экраны входа, навигация панели без раздела заявок и форма смены пароля.

## 3. Как это работает

### JWT и cookie

При успешном входе `POST /api/admin/login` создаёт JWT через `jose` (HS256). Payload содержит `sub` (ID администратора), `login`, `role: "admin"`, `iat`, `exp`, `iss: "remzona-admin"` и `aud: "remzona-admin"`. Токен подписан ключом `SESSION_SECRET`, который должен иметь минимум 32 символа. Срок `exp` — 7 суток.

Ответ устанавливает cookie `remzona_admin_session` с параметрами `httpOnly: true`, `sameSite: "lax"`, `path: "/"`, `maxAge: 604800`; `secure` включён при `NODE_ENV=production`. Cookie не доступна JavaScript-коду браузера.

`proxy.ts` проверяет подпись, алгоритм, issuer/audience, роль, subject и срок JWT для `/admin/**` и `/api/admin/**`. Валидный токен пропускает запрос; недействительный/отсутствующий токен перенаправляет страницу на `/admin/login` либо получает JSON 401. Next.js 16 переименовал convention `middleware.ts` в `proxy.ts`; в проекте применено актуальное имя, поскольку `middleware` deprecated.

`requireAdmin()` в `src/lib/auth.ts` повторно читает cookie через async `cookies()` и проверяет JWT. Защищённый layout использует этот guard дополнительно к proxy. Все закрытые API handlers (`logout`, `password`) также вызывают guard внутри handler; для будущих admin handlers обязательно делать так же.

### Вход и brute-force

Логин проверяется по точному значению `AdminUser.login`; пароль — `bcrypt.compare`. Если пользователя нет, всё равно выполняется bcrypt compare с фиктивным hash cost 12. Ответ при неизвестном логине и неверном пароле одинаковый: HTTP 401 и `Неверный логин или пароль.`

Ограничитель хранит число ошибок по хешированному ключу IP+нормализованный логин: 5 неверных попыток в течение 15 минут. Пятая ошибка отвечает обычным 401; следующая попытка получает 429 и `Retry-After`. Успешный вход сбрасывает счётчик. Записи очищаются по истечении окна, размер хранилища ограничен 10 000 ключами.

### CSRF

Все изменяющие admin API проверяют Origin (если передан) относительно `SITE_URL`, `Host` либо `X-Forwarded-Host` относительно host из `SITE_URL`, а также отклоняют `Sec-Fetch-Site: cross-site`. Это применяется к login, logout и смене пароля. Cookie дополнительно использует `sameSite=lax`. За reverse proxy `X-Forwarded-Host` должен задаваться доверенным nginx, а не приниматься безусловно от клиента.

### Смена пароля

Password endpoint находит администратора по `sub` проверенной сессии, сравнивает текущий пароль, требует новый пароль от 10 символов и совпадающее подтверждение, затем сохраняет bcrypt hash cost 12. После успешной смены текущая cookie удаляется, UI перенаправляет на `/admin/login`; повторный вход выполняется новым паролем.

## 4. Интерфейсы

### Защищённые маршруты

| Маршрут                                   | Доступ                                                                                                                                                        |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/admin`                                  | Требует JWT; перенаправляет на `/admin/services`.                                                                                                             |
| `/admin/services/**`                      | Требует JWT. На данном этапе список — заглушка.                                                                                                               |
| `/admin/settings/**`                      | Требует JWT. Настройки пока заглушка; `/admin/settings/password` готов.                                                                                       |
| `/api/admin/**`, кроме `/api/admin/login` | Требует JWT; без сессии proxy возвращает `401 application/json`. Все route handlers с изменением данных дополнительно вызывают `requireAdmin()` и CSRF guard. |
| `/admin/login`                            | Публичный экран входа, всегда `noindex,nofollow`.                                                                                                             |
| `POST /api/admin/login`                   | Публичная точка аутентификации, защищена same-origin проверкой и rate limit.                                                                                  |

### API

`POST /api/admin/login`

Тело JSON:

```json
{ "login": "admin", "password": "пароль" }
```

Успех: HTTP 200 `{"ok":true}` и `Set-Cookie: remzona_admin_session=...`. Ошибки: 400 некорректный JSON/пустые поля; 401 `Неверный логин или пароль.`; 403 same-origin отказ; 413 тело больше 16 KiB; 429 превышен лимит с `Retry-After`.

`POST /api/admin/logout`

Тело не требуется. Успех: HTTP 200 `{"ok":true}` и истёкшая cookie с теми же `path`, `sameSite`, `secure`. Ошибки: 401 без сессии, 403 CSRF отказ.

`POST /api/admin/password`

Тело JSON:

```json
{
  "currentPassword": "старый",
  "newPassword": "не менее 10 символов",
  "confirmation": "не менее 10 символов"
}
```

Успех: HTTP 200 `{"ok":true}`, bcrypt hash обновлён и текущая cookie удалена. Ошибки: 400 invalid JSON/валидация/несовпадение подтверждения/неверный текущий пароль; 401 отсутствует или потеряна запись администратора; 403 CSRF отказ.

Все API-ошибки возвращают объект `{ "error": "..." }`. В панели нет маршрута и пункта «Заявки».

### UI

`LoginForm` не принимает props; отправляет логин/пароль через `fetch`, блокирует повторный submit, показывает русскую ошибку и переходит на `/admin/services` после успеха. `PasswordForm` аналогично отправляет текущий пароль, новый и подтверждение. `LogoutButton` вызывает POST logout и возвращает на login.

## 6. Принятые решения и отклонения от плана

- Использован `proxy.ts`, а не `middleware.ts`, так как установленный Next.js 16 помечает middleware convention устаревшим и официально переименовал его в Proxy. Поведение соответствует требованию ранней защиты маршрутов.
- Proxy проверяет только подписанный JWT и не обращается к Prisma; каждый API handler повторно проверяет cookie через `requireAdmin()`. Админ layout тоже повторяет проверку. Это не связывает proxy bundle с DB клиентом.
- `/admin/login` вынесен в route group без меню панели; закрытые маршруты находятся в отдельной группе. Это сохраняет независимый UI и не меняет публичный маршрут.
- Rate limit in-memory: подходит одному Node-процессу. При нескольких инстансах/перезапусках счётчик не общий и нужен общий Redis/БД store.
- На этом этапе страницы услуг и настроек остаются заглушками, кроме смены пароля: их содержимое относится к этапам 4 и 10.
- Изменение пароля завершает текущую сессию. Другие уже выданные JWT не отзываются мгновенно: они остаются валидны до `exp` (не более 7 дней), поскольку отдельная версия/ревокация сессии не входит в текущую схему БД.

## 7. Как проверить

1. Убедиться, что `.env` содержит `SESSION_SECRET` минимум 32 символа, `SITE_URL`, а администратор создан `npm run db:seed`.
2. Запустить `npm run dev`, открыть `/admin`; ожидается redirect на `/admin/login`.
3. Открыть `/api/admin/password` без cookie методом POST; ожидается JSON 401 от proxy.
4. Неверный логин и неверный пароль должны показывать один и тот же текст и статус. После пяти неудачных попыток для одного IP+логина следующая должна получить 429; иной логин/IP не блокируется этим ключом.
5. Войти правильными данными. В DevTools cookie должна иметь HttpOnly, SameSite=Lax, Path=/ и Secure в production. `/admin` открывает панель; `/admin` перенаправляет на список услуг.
6. Выйти и проверить, что cookie удалена, защищённые страницы снова требуют вход.
7. В `/admin/settings/password` проверить неверный текущий пароль, пароль короче 10 символов и несовпадающее подтверждение; затем успешно сменить пароль. Ожидается logout и вход только новым паролем.
8. Отправить защищённый POST с посторонним Origin/Host либо `Sec-Fetch-Site: cross-site`; ожидается 403.
9. Проверить исходный HTML login: присутствует robots noindex/nofollow. Публичная `/` не использует компоненты админки.

Автоматическая команда `npm run test:auth` проверяет подписание/проверку/истечение JWT, ограничитель попыток, CSRF origin и fetch-site, redirect защищённой страницы, API 401, исключения login routes и проход запроса с валидной cookie. Проверки входа против реального AdminUser и смены пароля требуют доступной MySQL и выполненного seed.

Выполнена также HTTP-smoke-проверка production build: `/admin/services` без cookie вернул 307 на `/admin/login`; `/admin/login` вернул 200 и HTML meta `robots=noindex,nofollow,nocache`; `POST /api/admin/password` без cookie вернул JSON 401. Реальный вход/смена пароля через БД не прогонялись, поскольку локальный MySQL недоступен.

## 8. Ограничения и что нужно знать на следующих этапах

- Proxy — маршрутизационная защита, не замена `requireAdmin()` внутри будущих admin API handlers и server actions.
- За reverse proxy Host forwarding должен быть доверенно настроен. Настройка origin сверяется с `SITE_URL`; ошибочная схема/порт дадут 403.
- В памяти один экземпляр rate limiter; при горизонтальном масштабировании нужен общий storage и атомарные операции с TTL.
- Rate limit идентифицирует IP через `X-Real-IP`, затем первый `X-Forwarded-For`; фронтовой proxy обязан перезаписывать эти заголовки, иначе клиент может подделывать адрес.
- Подмена `SESSION_SECRET` завершает все текущие сессии; после ротации секрета администратор входит снова.
- Logout удаляет cookie браузера. Копия токена, украденная ранее, остаётся валидной до истечения срока; мгновенный revoke/глобальный logout потребуют session version/store.
- MySQL в текущем окружении не была доступна на `127.0.0.1:3306` на этапе проверки БД; проверить реальные bcrypt credentials и смену password можно после запуска MySQL и seed.
- Поля `ADMIN_LOGIN`/`ADMIN_PASSWORD` используются для первоначального seed; изменение `.env` само по себе не обновляет существующую запись администратора.
