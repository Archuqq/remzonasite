# Этап 13 — Переход с MySQL на PostgreSQL

> Это промежуточная конфигурация. На этапе 14 Prisma и PostgreSQL удалены; текущие данные хранятся в JSON-файлах. Не используйте инструкции ниже для текущего деплоя.

## Что изменено

- Prisma provider и migration lock переключены на `postgresql`.
- MySQL baseline заменён новой PostgreSQL initial migration для тех же моделей: `AdminUser`, `Service`, `Setting`.
- Локальный Compose запускает PostgreSQL 17; порт опубликован только на `127.0.0.1`.
- `.env.example` и проверка `DATABASE_URL` используют формат PostgreSQL.
- Запросы приложения остаются на Prisma Client, поэтому бизнес-логика CRUD не меняется.

## Локальный запуск

Создайте `.env` из `.env.example`, если его ещё нет, либо обновите только нужные переменные. Не заменяйте существующий `.env` целиком: в нём могут быть production-настройки.

```env
DATABASE_URL="postgresql://USER:PASSWORD@127.0.0.1:5432/DB_NAME?schema=public"
POSTGRES_DB="DB_NAME"
POSTGRES_USER="USER"
POSTGRES_PASSWORD="LOCAL_PASSWORD"
POSTGRES_PORT="5432"
```

Если пароль содержит специальные символы, URL-кодируйте его в `DATABASE_URL`. Затем выполните:

```bash
docker compose up -d postgres
npm run db:deploy
npm run db:seed
npm run dev
```

`db:seed` создаёт начального администратора и стартовые услуги только там, где их ещё нет. Он не переносит содержимое старой БД.

## Production

Нужен доступный приложению PostgreSQL и Node.js-процесс. В окружении production задайте `DATABASE_URL` от PostgreSQL, остальные секреты проекта, `SITE_URL` и постоянный `UPLOADS_DIR`; затем установите зависимости, примените миграции `npm run db:deploy`, соберите приложение и перезапустите Node.js.

phpMyAdmin управляет MySQL/MariaDB и не является панелью PostgreSQL. Если тариф REG.RU предоставляет только MySQL, эта конфигурация на нём работать не будет: потребуется PostgreSQL-сервис у хостера/другого провайдера или VPS с PostgreSQL. Проверяйте также сетевой доступ от Node.js-приложения к серверу БД.

## Перенос данных из MySQL

Переключение схемы не переносит существующие записи. PostgreSQL initial migration создаёт пустые таблицы; MySQL-дамп нельзя напрямую восстановить через `psql`. Переносите данные отдельно через проверенный конвертер MySQL → PostgreSQL (например, `pgloader`) или контролируемый export/import.

Перед переносом:

1. Сделайте резервную копию MySQL и папки `UPLOADS_DIR`.
2. Поднимите отдельную PostgreSQL-базу и проверьте перенос на ней.
3. Сохраните связи `Service.image` с файлами `uploads/services/`; сами изображения не хранятся в БД.
4. Проверьте количество строк, услуги, настройки и возможность входа администратора.
5. Только после проверки переключите production `DATABASE_URL` и DNS/приложение при необходимости.

Существующая MySQL-база и её migration history этой веткой не изменяются. Новую миграцию применяйте только к PostgreSQL. Для надёжного переключения без потери изменений нужен короткий режим обслуживания или повторная синхронизация записей перед переключением.

## Безопасность

Не коммитьте `.env`, не публикуйте пароли БД или администратора. Пароли, попавшие в переписку, нужно сменить в панели хостинга и в production environment; после смены пароля БД обновите `DATABASE_URL`.
