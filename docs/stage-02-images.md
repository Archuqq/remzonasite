# Этап 2 — Обработка и хранение фотографий

## 1. Что сделано

- Реализован серверный конвейер фото услуг на Sharp с проверкой фактического формата, ограничением размера/разрешения, EXIF-поворотом и удалением метаданных.
- Для каждого изображения создаются две версии WebP 2:1: 1200×600 и 600×300; оригинал не сохраняется.
- Добавлены SVG-заглушка и защищённый маршрут выдачи загруженных WebP-файлов.
- Добавлен генератор адаптивных Hero-файлов WebP/AVIF и blur data URL из исходного Mercedes PNG.
- Добавлены исполняемые тесты на форматы, прозрачность, лимиты и ошибки декодирования.

## 3. Как это работает

### Фото услуг

`saveServiceImage(buffer: Buffer): Promise<string>` проверяет размер до декодирования (не более 10 MiB), затем читает формат из содержимого с помощью Sharp, не доверяя имени файла или заявленному MIME. Разрешены JPEG, PNG, WebP и HEIF-контейнер, если текущая сборка Sharp может его декодировать. Предел разрешения — 40 000 000 пикселей.

Для каждой загрузки создаётся случайный UUID через `crypto.randomUUID()`. Sharp применяет `rotate()` для EXIF orientation, затем `flatten({ background: "#F7F7F5" })` для прозрачных областей, центральный `fit: "cover"` кроп и кодирование WebP с quality 80 / effort 5. Выходы: `UPLOADS_DIR/services/{uuid}-1200.webp` (1200×600) и `{uuid}-600.webp` (600×300). Оригинал и метаданные в итоговые файлы не попадают. При сбое любой записи удаляются обе возможные частичные версии. Успешный результат функции — UUID для поля `Service.image`.

`deleteServiceImage(id: string): Promise<void>` удаляет оба размера; отсутствующие файлы допустимы. Для непустого ID проверяется UUID, поэтому он не может использоваться для path traversal.

`getServiceImageUrls(id)` возвращает `{ src1200, src600 }`. Для UUID это `/uploads/services/{uuid}-1200.webp` и `/uploads/services/{uuid}-600.webp`. Для пустого или некорректного ID оба URL указывают на `/images/service-placeholder.svg`.

### Заглушка

`public/images/service-placeholder.svg` имеет `viewBox="0 0 1200 600"`, фон `#F2F2F0` и графитовый тонкий контур автомобиля по центру. Пропорция совпадает с фотографиями 2:1; генерация отдельного bitmap не требуется.

### Отдача

`GET /uploads/{path...}` работает в Node runtime. Разрешён только путь `services/{uuid}-{600|1200}.webp`. Проверяются и разрешённые сегменты, и `realpath` целевого файла относительно корня `UPLOADS_DIR`; symlink наружу из каталога не обслуживается. Успех возвращает `image/webp` с `Cache-Control: public, max-age=31536000, immutable` и `X-Content-Type-Options: nosniff`. Неверный путь, запрещённое расширение, отсутствующий файл и ошибка чтения возвращают 404 без раскрытия абсолютного пути.

В production предпочтительна прямая отдача `/uploads/` через nginx из того же `UPLOADS_DIR`; handler остаётся для разработки и как fallback.

### Hero

`npm run images:hero` читает `assets-source/hero-mercedes.png`, сохраняет размеры 640, 1024, 1600 и 1920 px в WebP (quality 80, effort 6) и AVIF (quality 55, effort 7) в `public/images/`, выводит размеры файлов и генерирует `src/lib/hero-blur.ts` с размытым WebP data URL шириной 24 px.

Фактический результат генерации исходника 1671×941:

| Ширина |     WebP |    AVIF | Размер кадра |
| ------ | -------: | ------: | ------------ |
| 640    |  36.3 KB | 21.2 KB | 640×360      |
| 1024   |  70.3 KB | 42.1 KB | 1024×577     |
| 1600   | 125.4 KB | 74.3 KB | 1600×901     |
| 1920   | 147.4 KB | 90.0 KB | 1920×1081    |

Blur data URL занимает около 0.1 KB. Вариант WebP 1600 px легче ориентира 250 KB.

## 4. Интерфейсы

### HTTP-маршрут

| Метод и путь                             | Запрос                                | Успех                                                      | Ошибки                                                                                                |
| ---------------------------------------- | ------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `GET /uploads/services/{uuid}-600.webp`  | Без тела; UUID и размер входят в URL. | `200`, `Content-Type: image/webp`, immutable cache на год. | `404 Not found` при недопустимом имени/расширении, отсутствующем файле или пути за пределами uploads. |
| `GET /uploads/services/{uuid}-1200.webp` | Аналогично для крупного варианта.     | Аналогично.                                                | Аналогично.                                                                                           |

Иных API-маршрутов этапа нет; вызов загрузки через admin API относится к этапу CRUD услуг.

### TypeScript API

```ts
saveServiceImage(buffer: Buffer): Promise<string>
deleteServiceImage(id: string): Promise<void>
getServiceImageUrls(id: string | null | undefined): {
  src1200: string;
  src600: string;
}
```

Ошибки загрузки представлены `ServiceImageError` с русским сообщением. Слой API следующих этапов должен преобразовать их в соответствующий HTTP-ответ.

## 6. Принятые решения и отклонения от плана

- Тесты реализованы через `tsx` и Node assert, без дополнительного Vitest: сценарии запускают реальные Sharp decode/encode и проверяют размеры результата.
- Установлен пиксельный предел 40 MP для защиты памяти во время декодирования.
- Поддержка HEIC зависит от сборки libvips. Код распознаёт HEIF ISO-BMFF brand и возвращает специальную понятную ошибку, если Sharp не может прочитать контейнер. У текущего Sharp `heif` заявлен с alias `.avif`; реального HEIC-файла в тестовой среде не было, поэтому фактическое декодирование HEIC не подтверждено. JPEG, PNG и WebP проверены.
- Исходник Hero шириной 1671 px масштабируется до обязательного 1920 px варианта. Размер файла корректен для srcset, но детализация выше исходного разрешения не появляется.
- Route Handler проверяет реальный путь после `realpath`, чтобы блокировать symlink за пределы upload root.

## 7. Как проверить

1. Запустить `npm run test:images`. Проверяются вертикальный JPEG 300×700, панорамный WebP 1600×300, квадратный PNG, прозрачный PNG, JPEG с EXIF orientation, не-картинка, HEIC-сигнатура, файл более 10 MiB и изображение более 40 MP.
2. Для обычных входов тест проверяет, что обе версии — WebP ровно 1200×600 и 600×300. Для полностью прозрачного PNG проверяется итоговый RGB-пиксель `[247, 247, 245]`; для EXIF JPEG проверяется поворот/нормализация и отсутствие metadata в выходном файле.
3. Запустить `npm run images:hero`; проверить восемь Hero-файлов и `src/lib/hero-blur.ts`; 1600 WebP должен быть меньше 250 KB.
4. Вызвать `saveServiceImage` при заданном `UPLOADS_DIR` и без него: каталог `services/` должен создаваться автоматически. `deleteServiceImage` удаляет оба варианта и допускает повторный вызов.
5. Тест напрямую вызывает GET handler для созданного файла и проверяет WebP body, MIME, Cache-Control и запрет `.jpg`. Дополнительно открыть URL через работающий Next.js сервер; неправильное расширение, traversal, случайный UUID и отсутствие файла должны дать 404.
6. Проверить `getServiceImageUrls("")` и URL для UUID; пустое значение ведёт к SVG-заглушке.

В этой среде выполнены image tests, включая прямой вызов GET handler для заголовков/тела ответа и запрета `.jpg`, генерация Hero и `npm run typecheck`. Числа размера в документации выведены генератором фактических файлов. Запрос через запущенный Next.js сервер вручную не выполнялся.

## 8. Ограничения и что нужно знать на следующих этапах

- Форма и admin API загрузки появятся на следующих этапах; сейчас реализована серверная инфраструктура обработки/отдачи.
- Файлы immutable-кэшируются на год, поэтому при замене фото нужно создавать новый UUID, не перезаписывать прежний.
- В БД хранится только UUID. Для восстановления нужны обе копии: БД и содержимое `UPLOADS_DIR`.
- Nginx body limit должен покрывать 10 MiB изображения плюс multipart overhead; план деплоя задаёт 12m.
- HEIC нужно проверять на целевой платформе. Не принимайте файл по расширению/MIME, если сборка Sharp его не декодирует.
- `public/images/hero-*` и `src/lib/hero-blur.ts` генерируются повторно через `npm run images:hero`; ручные изменения сгенерированных blur данных будут затёрты.
- При настройке nginx alias он должен указывать на тот же каталог, что и `UPLOADS_DIR`.
