КОНТЕКСТ ДЛЯ ЧЕЛОВЕКА (не для ИИ, просто для вас)
---------------------------------------------------
Раньше в проекте была MySQL, затем по вашей просьбе её заменили на PostgreSQL
через Prisma. Причина нового решения: админ на сайте один, клиентских данных
и заявок в системе нет, а на вашем тарифе reg.ru нет ни готового PostgreSQL,
ни MySQL вас не устраивает — то есть любая отдельная СУБД добавляет либо
доплату, либо лишнюю сущность, которая вам не нужна по объёму данных.
Это самостоятельный этап, который можно вставить в план после последнего
выполненного (сейчас это, скорее всего, этап после услуг/карты — ИИ ниже сам
определит номер по docs/README.md). Копируйте промт целиком в новую сессию
ИИ-агента, который имеет доступ к текущему репозиторию проекта.

ЗАДАЧА ЭТАПА
Полностью убрать PostgreSQL и Prisma из проекта и заменить хранение данных
(карточки услуг и настройки сайта) на JSON-файлы на диске сервера. Причина:
единственный пользователь системы — администратор, клиентских данных и
заявок в проекте нет, объём контента — десятки записей. Отдельная СУБД для
этого избыточна и создаёт ненужную зависимость на хостинге. Фотографии
карточек как хранились файлами в UPLOADS_DIR, так и продолжают храниться —
эта часть не меняется.

ЧТО НЕ МЕНЯЕТСЯ (чтобы не сломать лишнего)
  - Конвейер фото (sharp, UPLOADS_DIR, /uploads/[...path] route) — без
    изменений.
  - Публичные страницы, компоненты, дизайн, кнопки «Позвонить» — без
    изменений в разметке. Меняется только то, ОТКУДА данные приходят.
  - Формат данных на выходе (DTO для API и пропсы компонентов) должен
    остаться прежним, чтобы не переписывать компоненты, которые их
    потребляют.
  - Кэширование Next.js (unstable_cache с тегами "services" и "settings",
    revalidateTag/revalidatePath после мутаций) — паттерн сохраняется,
    просто источник данных внутри функции чтения меняется с Prisma-запроса
    на чтение JSON-файла.

ЧТО СДЕЛАТЬ

1. Общий модуль хранилища — src/lib/json-store.ts:
   - readJsonFile<T>(filePath, schema: ZodSchema<T>, fallback: T): читает
     файл, парсит JSON, валидирует через zod; если файла нет — создаёт его
     с fallback-значением и возвращает fallback; если файл повреждён —
     бросает понятную ошибку (не молчит и не стирает данные молча).
   - writeJsonFile<T>(filePath, data: T): атомарная запись — пишет во
     временный файл рядом (`${filePath}.tmp-${randomUUID()}`) и делает
     rename() поверх целевого файла (rename атомарен на уровне файловой
     системы — при падении процесса посреди записи старый файл не
     повреждается).
   - Мьютекс на запись по каждому пути: Map<string, Promise<void>> —
     каждая новая запись в тот же файл выстраивается в очередь за
     предыдущей (простой promise chaining), чтобы два одновременных
     admin-запроса не гонялись друг за другом и не затирали правки друг
     друга. Опиши это явно в комментариях.
   - getDataDirectory(): читает DATA_DIR из окружения (по умолчанию
     ./data), резолвит абсолютный путь, создаёт директорию при
     необходимости (mkdir рекурсивно).

2. Переменные окружения:
   - Убери DATABASE_URL из .env.example и src/lib/env.ts.
   - Добавь DATA_DIR (по умолчанию ./data) — по аналогии с UPLOADS_DIR.
   - Добавь ADMIN_LOGIN и ADMIN_PASSWORD (уже могут существовать с прошлых
     этапов — если да, не дублируй, просто убедись, что они используются
     по описанной ниже логике первичного посева).
   - .gitignore: добавь /data (это реальные данные экземпляра приложения,
     как и /uploads — не должны попадать в git).

3. Услуги (src/lib/services.ts) — перепиши хранение:
   - Файл data/services.json: массив объектов с теми же полями, что были в
     модели Service (id, slug, category, title, description, price,
     duration, image, imageAlt, sortOrder, isPublished, createdAt,
     updatedAt). Опиши zod-схему для одной услуги и для массива.
   - id генерируй через crypto.randomUUID() (замена Prisma cuid()).
   - createdAt/updatedAt — ISO-строки, проставляются в коде (updatedAt —
     при каждой записи).
   - CRUD-операции (создание/обновление/удаление/publish/reorder), которые
     раньше шли через `prisma.service.*` в admin API-роутах (см. список,
     который ты собрал в начале, вероятно src/lib/admin-services.ts и
     route-файлы под src/app/api/admin/services/**), перепиши так: читают
     весь массив через readJsonFile, меняют его в памяти (immutable —
     создавай новый массив/объект, не мутируй), пишут обратно целиком через
     writeJsonFile. Для reorder — просто пересчитай sortOrder по новому
     порядку id и сохрани весь массив.
   - getPublishedServices() (публичная сторона) и getServiceById/список
     для админки — фильтрация и сортировка (isPublished, sortOrder) теперь
     делаются в JS после чтения файла, а не в БД-запросе. Оберни публичное
     чтение в unstable_cache с тегом "services", как было.
   - slug остаётся уникальным — проверяй уникальность по всему массиву при
     создании (как раньше проверял уникальность в БД).

4. Настройки (src/lib/settings.ts) — перепиши хранение:
   - Файл data/settings.json: плоский объект с теми же ключами, что были в
     таблице Setting (phone, phone_href, address, hours_weekdays,
     hours_weekend, yandex_org_id, reviews_enabled, site_name).
   - getSettings() — оборачивается в unstable_cache с тегом "settings",
     читает JSON, дополняет отсутствующие ключи значениями из
     DEFAULT_SETTINGS (как было).
   - updateSettings(patch) — читает текущий файл, мержит patch, пишет
     обратно целиком, вызывает revalidateTag("settings", "max") — логика
     та же, что была с Prisma-upsert, просто без БД.
   - Если файла ещё нет (первый запуск) — создай его со значениями
     DEFAULT_SETTINGS при первом чтении (readJsonFile это уже умеет по
     п.1).

5. Администратор — убери таблицу AdminUser, замени на data/admin.json:
   - Файл data/admin.json: { login: string, passwordHash: string }.
   - Логика первичного посева: если файла нет — при первом обращении к
     функции аутентификации (или отдельным скриптом, см. п.6) создай его из
     переменных окружения ADMIN_LOGIN и ADMIN_PASSWORD (bcrypt-хеш, cost
     12), затем работай только с файлом. Это сохраняет уже существующую
     функциональность «сменить пароль» в /admin/settings/password — после
     смены пароль пишется в data/admin.json, а не в БД, и переживает
     деплой (просто убедись, что DATA_DIR — вне папки, которую перезаписывает
     деплой, см. п.8).
   - src/lib/auth.ts (или где сейчас идёт bcrypt.compare против записи из
     Prisma) — перепиши на чтение data/admin.json через json-store.
   - ВАЖНО: data/admin.json никогда не должен быть доступен по HTTP ни
     через один route. Явно проверь, что ни один существующий обработчик
     (включая /uploads/[...path]) не резолвит пути внутрь DATA_DIR — только
     UPLOADS_DIR можно отдавать наружу. Если есть сомнение — добавь тест.

6. Скрипты npm (обнови package.json):
   - Удали: db:migrate, db:deploy, db:seed, db:studio и postinstall
     (prisma generate), если он был только ради Prisma.
   - Удали зависимости @prisma/client и prisma (dependencies и
     devDependencies).
   - Добавь data:seed (например `tsx scripts/seed-data.ts`) — идемпотентный
     скрипт: если data/services.json нет — создаёт его с теми же 6 демо-
     услугами, что были в prisma/seed.ts (Компьютерная диагностика, Плановое
     ТО, Тормозная система, Подвеска, Кондиционер, Кузовной ремонт и
     покраска), без фото (image: ""); если data/settings.json нет — создаёт
     его со значениями по умолчанию из base-контекста (адрес «г. Серпухов,
     Советская улица, 2кА», yandex_org_id «73425839561» и т.д.); если
     data/admin.json нет — создаёт его из ADMIN_LOGIN/ADMIN_PASSWORD. Если
     файлы уже есть — ничего не трогает и сообщает об этом в консоли.
   - Добавь hash:password (`tsx scripts/hash-password.ts <пароль>`) —
     утилита на случай ручного восстановления доступа: печатает bcrypt-хеш,
     который можно вручную вписать в data/admin.json на сервере, если
     администратор забыл пароль и .env недоступен для пересева.

7. Удаление Prisma из проекта:
   - Удали папку prisma/ (schema.prisma, migrations/, seed.ts) и
     src/lib/db.ts.
   - Удали docker-compose.yml или, если в нём было что-то ещё кроме БД,
     убери из него только сервис Postgres/MySQL; если файл становится
     пустым по смыслу — удали целиком и напиши об этом в документации.
   - Пройдись по всем файлам из списка в начале (импорты `@/lib/db`,
     `PrismaClient`, `@prisma/client`) и убедись, что ни одного упоминания
     Prisma не осталось (`grep -rn "prisma" src` и `grep -rn "@prisma" .`
     после удаления зависимостей должны быть пустыми, за исключением
     самой этой документации).
   - Проверь next.config.ts и любые другие конфиги на предмет
     Prisma-специфичных настроек (например serverExternalPackages) и
     убери лишнее.

8. Продакшен и бэкапы (обнови docs/stage-12-deploy.md или аналогичный файл,
   если он есть, — см. п. «документация» ниже):
   - На сервере DATA_DIR должен быть вне папки деплоя (по аналогии с
     UPLOADS_DIR), например /var/www/remzona/data, чтобы `git pull` +
     передеплой не затирали контент.
   - Права доступа: data/ (и особенно admin.json) должен быть читаем/
     записываем только пользователем, от которого запущен Node-процесс —
     не 777.
   - Бэкап: ежедневный tar каталогов data/ и uploads/ (cron), хранение
     7–14 дней — вместо mysqldump/pg_dump, который был нужен раньше.
     Восстановление — просто распаковать архив обратно на место.
   - Инструкция по установке на reg.ru (или любой Node-хостинг) теперь НЕ
     требует шага «поднять и настроить СУБД» — явно вычеркни этот шаг из
     существующей инструкции по деплою и отметь, что теперь достаточно
     Node.js без базы данных.

9. Проверка перед завершением:
   - npm run build, lint, typecheck проходят без ошибок и без упоминаний
     Prisma.
   - С нуля (пустой data/): npm run data:seed создаёт три файла с
     корректным содержимым; сайт открывается, показывает 6 услуг без фото
     (заглушка), настройки — значения по умолчанию.
   - /admin: вход по ADMIN_LOGIN/ADMIN_PASSWORD работает при первом
     запуске (посев admin.json); смена пароля в /admin/settings/password
     сохраняется и переживает перезапуск процесса (`npm run build && npm
     start` заново — пароль остаётся новым, а не сбрасывается к env).
   - Создание/редактирование/удаление/reorder/publish карточки в
     /admin/services — сразу отражается на публичной странице (проверь,
     что revalidateTag/revalidatePath по-прежнему работают).
   - Два быстрых подряд сохранения в админке (например, дважды нажать
     «Сохранить» в разных вкладках) не портят JSON-файл — за счёт мьютекса
     из п.1.
   - Ручное повреждение JSON (специально сломать синтаксис в
     data/services.json) даёт понятную ошибку в логах/на странице, а не
     падение всего процесса без объяснений.
